Migration drift detection for knex

knex-drift

Catch the migration problems that knex cannot see.

A standalone CLI that checksums every migration file against the knex_migrations ledger. It never runs DDL, and it never modifies that ledger.

Quick start GitHub

node >= 22 knex >= 2 (peer) zero config reads only MIT

The problem#

knex records only the name of every migration it runs. It never records what the file contained, and it never looks at the database.

So knex stays silent in all four of these cases. Every one of them makes a rebuilt database differ from production, and you find out much later.

  • D3 A migration file is edited after it was applied.
  • D4 A new file is inserted out of order.
  • D5 A ledger row is duplicated.
  • D7 Someone points a fresh ledger at a database that already has tables.

knex-drift closes that gap. It is a standalone CLI, because the knex CLI has no plugin hook. It never runs DDL, and it never modifies knex_migrations.

Install#

Requires Node 22 or newer, and knex 2 or newer as a peer dependency.

What it detects#

Findings and severity
Code Condition Severity
D3 A migration file changed after it was applied blocking
D4 A pending migration sorts before the newest applied one blocking
D5 The same migration name appears in the ledger more than once blocking
D7 The ledger is empty but the database already holds user tables blocking
D2 A ledger row has no matching migration file warning
UNVERIFIED Applied migrations that have no recorded checksum yet note

Commands#

knex-drift verify

Compares the migration files with the ledger. Reads only — it writes nothing.

verify options
Option Effect
--strict Treat warnings as blocking
--json Print machine-readable output
--pre Run only the checks that are safe before a migration (the default today)
-c, --config <path> Path to drift.config.js
--cwd <path> Directory to resolve paths from

knex-drift record

Stores the checksum of applied migrations in the sidecar table.

record options
Option Effect
--all Record every applied migration, not only the newest batch
-c, --config <path> Path to drift.config.js
--cwd <path> Directory to resolve paths from

Without --all, only the newest batch is recorded. That is what a deploy needs immediately after knex migrate:latest. Recording every migration at once is the deliberate adoption step, so it is explicit.

Exit codes#

Process exit codes
Code Meaning
0 Clean, or notes only
1 At least one blocking finding
2 Warnings only (becomes 1 under --strict)
3 The tool could not run — bad config, no connection

Programmatic use#

Do not use knex lifecycle hooks

Do not build the pre-migration check on knex's lifecycle hooks. knex calls beforeAll only when there are pending migrations, so a deploy with nothing to run would skip the check entirely.

Database support#

Dialect-independent

The checksum and ledger checks — D2, D3, D4, D5 and UNVERIFIED — work on any dialect.

Needs a catalog query

D7 lists user tables, and supports PostgreSQL, Redshift, MySQL/MariaDB, SQLite, MSSQL and Oracle. On an unrecognised dialect, D7 is skipped rather than guessed.

The automated test suite runs against SQLite via better-sqlite3.

Not implemented yet#

This release covers migration files against the ledger. It does not yet compare either of them against the live database schema.

The following are planned:

  • A catalog reader and a committed expected.schema.json, produced by replaying every migration onto a scratch database in CI
  • Phantom object detection — tables, columns and indexes present in the database that no migration created
  • drift-ignore.yml, with adopt / revert / ignore / quarantine classes
  • A baseline command for adopting a database that has already drifted
  • Custom migrationSource support; the tool currently reads the migrations directory itself
